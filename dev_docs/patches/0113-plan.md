# Patch 0113: Routegraph guidance (the app graph behind course correction)

Stacks on 0112. Not a training course: this is the engine under every course's off-course card. The living plan and log is `dev_docs/ROUTEGRAPH_GUIDANCE.md`.

## What you asked
> integrate the navgraph package so the app knows the correct courses of action to take to correct a user who has gone off task in the training module. Do not just map out corrections, map out the entire app... every screen, popup, effect, action, process, whatever, including user generated screens and their actions and/or gestures, screens defined at runtime, etc. It needs to actually understand the app as a whole. It also needs to account for different views, display modes, roles, etc.

## How it works
- **The app as a graph** (`src/app.navgraph`, `src/app.navschema`). Hand written, readable and diffable, in the format the VS Code navgraph parser understands. 68 screens (5 tabs, 2 Checkout views, 18 pushed pages, 39 sheets, 4 overlays) and 155 transitions, with each screen's `kind`/`label`/`tab`/`route`/`roles` and each transition's `say` (the words) / `gesture` / `spot`. Every tab is reachable from every other and every page from Checkout.
- **A bundleable mirror.** React Native has no filesystem, so `scripts/build-navgraph.ts` validates the file and writes `src/lib/appNavgraph.generated.ts` (the graph text plus the schema as a plain object). `npm run graph:build` regenerates it and `npm run graph:check` fails on drift; a test also compares the mirror with the file on disk.
- **Control level** (`src/lib/appControls.ts`). The graph holds screens and the way between them; this plain table holds which screen each control lives on and how it is used. Every static spot in `src/lib/trainingSpots.ts` and every dynamic prefix (`grid.item:`, `cart.line:`, `line.minus:`, `order.row:`, `refund.pick:`, `cash.denom:`, `scan.card:`, and the rest) is mapped, with `cart.line:` marked as a swipe. Tests keep the table honest against `trainingSpots.ts`, so a new spot can never go unplaced.
- **The engine** (`src/lib/appGraph.ts`). Builds the live tree once (`indexTreeFromText` with the schema), maps the app state to a node (`stateNode`: lock, a pushed route, a Checkout view, or the tab), maps a spot to its screen, plans a walk (`planRoute`) from where the person is to the screen the fix is on, and turns each step into the same `FixCandidate` the dock and overlay already draw (with the edge's own words and gesture). `roleCanReach` reads the screen's `roles`.
- **Wording is untouched.** `guidanceCandidates(deviation, snap, windowOpen)` returns `fixCandidates(...)` first, exactly and in order, then the graph's walk behind it (with any target the plain answer already names removed). The dock measures the first candidate that is really on screen. When the plain answer is reachable, nothing at all changes; the graph shows through only when the fix's own control is not on screen, pointing at the way back (Back, or the Checkout tab) instead of a dead card with no ring.
- **Runtime and user made screens.** Each tick `TrainingHost` puts the sale's cart lines on the graph (`syncRuntimeFromSnap`) and every control currently on screen (`registerRuntimeSpots(mountedSpotIds())`). `Spot.tsx` gained `mountedSpotIds()` (its own mount registry, plus the equal parts of a segmented control) and stays free of any graph knowledge. Because `Row`, `Btn`, `Chip` and `IconBtn` all register through the spot layer, this covers grid tiles, variations, cart lines and their sub controls, search results, customer rows, discount presets, order rows, refund picks and cash denominations with no change to any screen.
- **Guarded.** The tree is built in a `try`; if the graph ever fails to parse, `tree()` is null and guidance falls back to the old `fixCandidates` alone. A bad control registration is caught and skipped. Training can never be broken by the graph.
- **Tests** (`tests/appnavgraph.test.ts`, 18): the mirror matches the file, the graph validates, reachability, a direct tap between every pair of tabs, every static spot and dynamic prefix has a home, gestures, `stateNode`, role gating, the plain fix always leads with its own words, the window-close and the walk come behind it, runtime controls join with their gesture, the sale on the till puts its cart lines on the graph, unknown spots are handled honestly, and node ids are safe as screen ids.

## Not covered
Each cart line still shares the one `sheet_line` screen rather than getting its own cloned screen (`cloneTree`/`registerScreens`), because a walk is planned screen to screen and the line's own window is handled by the plain answer. The dock does not yet show a `repeat` count for a walk. The control-to-screen table is still a table; its last rough edges can move onto screen metadata once the graph is the only source. None of these change what a person sees today.
