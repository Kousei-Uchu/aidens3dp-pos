# Patch 0115: Routegraph per-instance scope (tag a product, a row, a user)

Stacks on 0114. Not a training course: this finishes the scope work by letting a *runtime instance* belong to a run, not just a screen or an edge. The living plan and log is `dev_docs/ROUTEGRAPH_GUIDANCE.md`.

## What you asked
> the training modules have their own item libraries and grid views and users and stuff, did we account for that too? ... a schema field on things to specify which training modules (if any) that each template-screen-instance (product, etc.) or screen variation is accessible from.

0114 tagged screens and edges. This patch tags the other half: the instances a run builds (a product tile, a customer row, a grid page, a practice user).

## The honest state of the practice world
- Every course runs the **one shared sandbox** (`buildSandbox` in `src/lib/trainingSandbox.ts`): the same item library (`FIXTURE_VARIANTS`), the same grid (Home and Extras), the same customers and the same practice drawer.
- Only four things differ per course today: `practiceStaff` (sign-in swaps in Casey and Morgan), `flow` (standard or guided checkout), `tabs`/`routes` (which screens the course allows) and per-goal `inject`s (a starting cart, a drawer, a decline).
- So there is no per-module item library, grid or user yet. The item library, the grid and the users are swapped **inside the same screens**, so they are not a place-scope concern: the screen is `tab_checkout` whichever data is under it. That is why 0114 tagged only the places that really differ (the camera and the practice pass).

## How it works
- **A runtime instance can carry a run tag.** `registerRuntimeSpots(spots)` now takes a spot id or `{ spot, modules }` (`RuntimeSpot` in `src/lib/appGraph.ts`). When `modules` is given it becomes the action node's metadata, which routegraph carries and `scopeFilter` already checks on the destination. So a tile registered as `{ spot: gridItemSpot('bee'), modules: ['scanning'] }` is reachable in the scanning run and refused everywhere else, exactly like a tagged screen.
- **No library change.** `registerActions` accepts `meta` on an action spec; routegraph stores it on the action node (`{ modules, kind: 'action', parent }`), and the same `edgeFilter` that drops an out-of-scope screen drops an out-of-scope instance.
- **Untagged means every run.** A plain spot id (the common case, and everything `syncRuntimeFromSnap` registers) is in every run, which is right while the sandbox is shared.
- **Tests** (`tests/appnavgraph.test.ts`, +2, 27 total): a tagged instance is in its run and refused in the everyday till and in another course; an untagged instance is in every run.

## Not covered
No instance is tagged yet, because no instance differs per course yet, so this is the capability rather than a visible change. Giving a course its own item library, grid pages or fake users is a separate, larger build (a module field plus `buildSandbox` work); the engine is ready for it (see "Still to do" in `dev_docs/ROUTEGRAPH_GUIDANCE.md`). The per-line window templating (`cloneTree`/`registerScreens`) and the dock's `repeat` count remain deferred, and none of it changes what a person sees today.
