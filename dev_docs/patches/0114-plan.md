# Patch 0114: Routegraph scope (a run only walks through places it has)

Stacks on 0113. Not a training course: this extends the guidance engine under every course's off-course card so a plan is kept inside the run it is for. The living plan and log is `dev_docs/ROUTEGRAPH_GUIDANCE.md`.

## What you asked
> add a schema field on things to specify which training modules (if any) that each template-screen-instance (product, etc.) or screen variation is accessible from, and modify the source of navgraph to include an optional filter parameter to filter for/out routes using or not pathing through screens with that tag, so it doesnt tell us to go through a training screen in the real app, or vice versa.

Per module tags (an array of module ids), not per model. Guidance runs both in a course and in the real till (Demo / Help), so both directions are filtered.

## How it works
- **A `modules` tag on screens and edges** (`src/app.navschema`). Values are a training module id (see `src/training/index.ts`) or the sentinel `"real"` for the everyday till. Empty or missing means every scope, so only the places that differ carry it: `overlay_camera` is `["real"]`, the practice pass `overlay_practice_pass` is `["sign-in"]`, and a new `overlay_practice_camera` (with `tab_checkout <-> overlay_practice_camera` for `scan.camera` / `scan.done`) is `["scanning"]`. `src/app.navgraph` grew to 69 screens, 157 transitions.
- **A scope, not a global mode** (`src/lib/appGraph.ts`). `GuideScope = { keys?, tabs?, routes? }`. `scopeForModule(mod)` returns `{ keys: [mod.id], tabs: mod.tabs, routes: mod.routes }`; `scopeForReal()` returns `{ keys: ['real'] }`; `undefined` means unfiltered (the old behaviour, kept for the plain tests).
- **The scope rule** (`metaInScope`, `screenInScope`). A place with no `modules` tag is in every scope. A tagged place is in scope only when the run's `keys` intersect its tags. A screen that names a `tab` or a `route` outside the run's `tabs`/`routes` is out of scope even with no tag, so a course never reaches a page its own definition disallows without hand-tagging every page.
- **No library change.** routegraph already applies an `edgeFilter` in both `findReachable` and the pathfinder (`PathOptions.edgeFilter`), so `scopeFilter(scope)` is handed straight to both. An edge is dropped when its destination screen is out of scope or the edge's own `modules` tag is.
- **Threaded through the walk.** `reachable`, `routeNavSteps`, `guidanceCandidates` and `planToSpot` all take an optional scope. A fix whose own place is outside the run adds no walk at all (the plain `fixCandidates` answer still leads). `TrainingHost` passes `scopeForModule(mod)`, so the off-course card for a course is planned against that course's world; the everyday till uses `scopeForReal()`.
- **A run's pretend controls do not linger.** `TrainingHost` calls `clearRuntimeSpots()` when the run ends, so a finished run's runtime nodes (cart lines, mounted spots) leave the graph and cannot colour the next plan.
- **Tests** (`tests/appnavgraph.test.ts`, +7 scope tests, 25 total): a place with no tag is in every run; the real and practice cameras are kept apart both ways; the practice pass exists only in the sign-in course; a course never reaches a page its routes disallow; a fix outside the run adds no walk; a practice-only control walks in through the practice camera and is refused elsewhere; runtime controls can be forgotten.

## Not covered
Each cart line still shares the one `sheet_line` screen rather than getting its own cloned screen (`cloneTree`/`registerScreens`); a scope already keeps such a walk inside the run that owns the window, so this remains about naming the exact window, not about scoping. Today only the camera (practice vs real) and the practice pass differ, so only they carry `modules`; future module-only screens should be tagged the same way. None of these change what a person sees today.
