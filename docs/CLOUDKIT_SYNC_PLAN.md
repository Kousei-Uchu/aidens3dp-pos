# CloudKit sync plan

Status: planning only, no code written yet.
Suggested location: `docs/CLOUDKIT_SYNC_PLAN.md`
Written against the `main` branch as cloned on 2026-10-19.

Note (19 October 2026): before this plan was started, the assistant's sales tools were widened to read every till, using the
metaobject rows that already exist (`sale_json` on `pos_sale`, plus the daily rollups), cached in `pos.shared`. That is the
interim path and it changes nothing here: CloudKit replaces the transport described in section 2, and section 6's sales sync
would supersede the interim pull rather than duplicate it. See `docs/GUESSES.md`, "Shop-wide sales view".

## 1. Goal

Replace "some data goes to Shopify metaobjects, polled by each register" with one synced store on CloudKit that:

- keeps every register in sync, including across **different Apple IDs**
- on first connection, **imports all existing shared data** (Shopify metaobjects and the appropriate local data)
- is **safe when several devices connect at the same time**
- keeps working offline, with changes syncing when the device reconnects

Shopify stays the source of truth for products, inventory, customers, orders and gift cards. Those are not copied into CloudKit.

## 2. How things work today (verified in the repo)

- State is one zustand store (`src/state/store.ts`) with four persisted slices: `settings`, `pos`, `grid`, `data`. Persistence goes through `persist()` to `kvSet` in `src/lib/kv.ts`, which is a thin wrapper over AsyncStorage.
- No backend. Shared state lives in Shopify metaobjects (`src/lib/shopify/metaobjects.ts`), polled by each register (`src/lib/sync.ts`).
- Metaobject types: `pos_saved_cart`, `pos_layout`, `pos_sale`, `pos_daily_rollup`, `pos_settings`.
- Conflicts are handled with `version` counters. Saved carts also carry `dirty`, `remoteId` and `locked_by`/`locked_at` (a soft lock). Shared settings use `sharedVersion` and `sharedSettingsPending`.
- Per-device identity keys are listed in `DEVICE_KEYS` in `src/lib/backupFile.ts`: `registerId`, `registerName`, `sharedVersion`, `sharedSettingsPending`, `scannerCalVersion`, `scannerCalPending`.
- Training and demo modes block writes with `kvWriteAllowed` (`trainingGuard`).
- Square history is stored in files via `src/lib/squareHistoryIO.ts` (packed JSON plus a manifest, meta key `squareHistoryMeta`).
- Expo SDK 54, React Native 0.81, bundle ID `com.aidens3dp.pos`, Apple team `HD264P8365`. The `ios/` folder is regenerated by `ios:reset`, so native config must live in `app.json` or config plugins, never hand-edited in `ios/`.

## 3. Decisions made

| Decision | Detail |
|---|---|
| Sync technology | CloudKit via a small local Expo module in Swift, wrapping `CKSyncEngine` (iOS 17+). |
| Multiple Apple IDs | One owner Apple ID holds a custom zone (`Store`) in its private database and shares it with a zone-wide `CKShare`. Other Apple IDs accept the share and use the shared database. Two sync engines: private and shared. |
| Public database | Rejected. Anyone with the app could read sales data. |
| Core Data / `NSPersistentCloudKitContainer` | Rejected. It would mean moving storage out of AsyncStorage, which is too invasive. |
| What CloudKit holds | POS-owned data only (see section 5). |
| Shopify metaobjects after migration | Left in place, untouched, as a read-only backup and rollback path. |
| Migration runner | Owner devices only. Participants cannot create zones, so they wait. |

## 4. Architecture

### 4.1 Sharing model

- The owner creates the zone and the share, and invites other Apple IDs (link or QR).
- Participants need share acceptance handled natively (AppDelegate subscriber for `userDidAcceptCloudKitShareWith`) and `CKSharingSupported` set in Info.plist.
- Entitlements (iCloud container, CloudKit) and `UIBackgroundModes: remote-notification` go in the config plugin.
- Limits and consequences:
  - a share supports up to 100 participants
  - the owner's iCloud quota pays for all data
  - ownership cannot be transferred, so losing the owner account loses the data (hence the Shopify backup)

### 4.2 Record naming (stable, deterministic)

Names are derived from IDs that already exist, so two devices importing the same row collide into the same record instead of creating a duplicate.

| Record type | Record name |
|---|---|
| Saved cart | `cart-<cart_uuid>` |
| Sale | `sale-<sale_uuid>` |
| Layout | `layout-<layout_key>` |
| Settings | `settings-<settings_key>` |
| Daily rollup | `rollup-<rollup_key>` |
| Migration state | `migration-v1` |

Imports use create-if-absent so an old import never overwrites a newer edit.

### 4.3 Code seams

- `persist()` and `kvSet` in the store are the natural place to queue record changes for synced slices.
- `sync.ts` and `metaobjects.ts` become one backend behind a common interface. The CloudKit backend replaces polling with push-driven change callbacks.
- `kvWriteAllowed` must also block CloudKit writes, so training and demo sessions never leak into real data.
- Handle iCloud being signed out or restricted (`CKAccountStatus`) with a clear fallback state.

### 4.4 Conflict handling

- Writes use `ifServerRecordUnchanged`. On `serverRecordChanged`, merge by field for carts and use last-writer-wins for settings.
- Sales are append-only with UUIDs, so they should not conflict.
- The existing `version`, `dirty`, `remoteId` and `locked_by` fields map onto change tags. The cart lock stays advisory only, because CloudKit has no transactions.

## 5. What syncs and what stays local

| Data | Action |
|---|---|
| Metaobjects: saved carts, layout, sales, rollups, settings | Migrate and sync |
| `settings`, shared parts (bundles, cart warnings, adjust perms, staff, receipt profile, inventory prefs) | Sync |
| `settings`, device parts (`DEVICE_KEYS`) | Stay local |
| `pos.saved` carts | Sync (unsynced `dirty` carts push from their own device) |
| `pos.cart` (the open cart) | Stay local |
| `grid` layout | Sync |
| `data` (catalogue and customer cache) | Do not migrate; derived from Shopify |
| Square history files | Sync as sharded `CKAsset`s with a manifest record |
| Theme, tile size, terminal pairing | Probably per-device (to confirm) |
| Shopify token, PINs, secure-store items | Stay local for now. Later option: end-to-end encrypted `encryptedValues` fields. |

## 6. First-connection migration

1. **Owner only.** Only a device on the owner's Apple ID creates the zone and share and runs the import.
2. **Lease record.** `migration-v1` is saved with `ifServerRecordUnchanged`, so only one device wins. It stores the device ID (`registerId`), a lease expiry with heartbeat, the current phase, and a cursor. If the holder dies, another owner device takes over using the record's change tag.
3. **Phases, in order:** settings, layout, saved carts, sales, rollups, Square history. Shopify lists are paged. Writes go in batches of about 100 records (CloudKit's cap is 400 per operation). Each batch advances the cursor so a crash resumes where it stopped.
4. **Verify.** Compare per-type counts between Shopify and CloudKit. Only then set `status: done`. Clients switch to the CloudKit backend only once they see `done`.
5. **Other devices during migration.** They show a "Setting up sync" state, queue local writes, and flush them once the import finishes.
6. **Settings conflicts.** The Shopify settings row is canonical on first import. Local settings are used only if no row exists. Where both exist, the highest `sharedVersion` wins.
7. **Rollback.** Metaobjects are untouched, and a backend flag lets the app revert. Optionally dual-write for a release or two. With only a few iPads, updating them all at once is likely simpler.

## 7. Known / unknown

### Known

- The persisted slices, the metaobject types and their fields, and `DEVICE_KEYS` (all read from the repo).
- No references to metaobjects were found in `receipt-server`, `gift-claim-server`, `pass-server` or `docs-server` (by grep for the type and function names only).
- Multiple Apple IDs requires the share-based design above.
- Simulator is unreliable for CloudKit push. Testing needs two physical devices on two Apple IDs.
- `npm run ios` builds use the **Development** CloudKit environment. TestFlight and App Store builds use **Production**, a separate and empty database. The schema must be deployed to Production, and the migration would run again there.

### Unknown resolved from the repo (19 October 2026)

- **Square history structure and size.** One gzip file per month (`sales-<YYYY-MM>.json.gz`) plus a small `manifest.json`. `squareHistory.ts` does the packing (`packMonths`, `buildManifest`, `packJson`); `squareHistoryIO.ts` writes them to `Documents/square-history/` and records the summary under the AsyncStorage key `squareHistoryMeta`. `squareShareIO.ts` already copies those same files to another register. So the shard is the existing month file, one `CKAsset` per month, with the manifest as one record, and no new packing is needed.
- **`sync.ts` behaviour.** Two directions behind one shape: an idempotent outbox (`processOutbox`, each step marked done) and a 25 s poll (`pollShared`) of saved carts, layout, shared settings, scanner calibration, shared drawer, warning list, and now other tills' sales and rollups. Conflicts use `version` counters; saved carts add `dirty`, `remoteId` and an advisory `locked_by`/`locked_at` lock; the drawer merges entry lists rather than replacing.
- **The four servers do not touch the metaobjects.** A content grep for the type names and the metaobject helpers across all four found nothing, so nothing there needs changing at cut-over.
- **Persisted keys.** Only the four slices (`settings`, `pos`, `grid`, `data`) and the literal `squareHistoryMeta`, plus a per-conversation assistant history key written from `src/screens/Assistant.tsx` (a local-only UI cache that should not sync). No other computed key exists.
- **iOS deployment target.** `app.json` sets no deployment target and installs no `expo-build-properties`, so Expo SDK 54's default applies, which is below iOS 17. `CKSyncEngine` needs iOS 17, so a config plugin must raise `ios.deploymentTarget` to `17.0`.
- **Which settings are per-device.** The shared set is exactly the seven keys in `pushSharedSettings` (`staff`, `bundlesJson`, `fees`, `cashRounding`, `requirePin`, `adjustPerms`, `cartWarnings`). Everything else is per-device, including the theme, tile size, screensaver, inventory prefs, help depth, assistant setup, receipt profile and location, plus `DEVICE_KEYS`. So the plan's "theme, tile size, pairing are probably per-device" is confirmed: they stay local and must not sync.

### Decided by the owner (19 October 2026)

- **Owner Apple ID:** the owner's personal Apple ID, not a shop-owned account. Section 8's single-point-of-failure risk stands, so the Shopify metaobjects stay in place as the backup and rollback path.
- **Platform:** iOS only. CloudKit stays the right transport, and no Android work is planned.

### Answered by the owner (20 October 2026, before patch 4)

- **Field encryption: plain fields for now, `encryptedValues` kept as a later option.** Sales are written unencrypted. The owner's reasoning is sound and is recorded here: it is easier to add encryption later than to remove it, so nothing is locked in by starting plain. Patch 4 therefore writes ordinary CloudKit fields, and the one helper that reads and writes a sale is kept small enough that switching a field to `encryptedValues` is a change in that helper, not a migration. The trade-off to remember: an encrypted field cannot be used in a `CKQuery` predicate, so a later switch moves anything queried server-side (totals, dates) off the encrypted side, which is why the plan already keeps rollups apart from the sale record.
- **Cut-over: decided at patch 8, not now.** Patch 4 keeps the metaobject backend live beside the CloudKit one, so the seam has two implementations in patch 4 and the backend flag arrives with the rollback work. Section 6's dual-write question is therefore open until then.
- **Privacy: an in-app note now, policy wording the owner's.** The Cloud sync page and its help page will say plainly what is stored in iCloud and what is not (see below). The shop's own privacy policy and the App Store privacy details stay the owner's to update; nothing in the code changes a policy.
- **iCloud storage: fine.** The owner's plan has ample headroom. The estimate stands for the record: this till keeps 2000 sales locally at roughly 1 to 3 KB of `sale_json` each, so a few thousand sales is a few MB, and Square history is one gzipped month file each (a repo test packs 400 sales under one eighth of their JSON). A few MB of sales plus a few MB a year of Square history is well inside the owner's plan.

### What is and is not in iCloud (for the in-app note)

Written to the owner's iCloud, shared with the registers that joined the shop: the shared settings (staff, bundles, fees, cash rounding, Require PIN, adjust permissions, cart warnings), the grid layout, saved carts, sales records and daily totals, the shared cash drawer, the scanner calibration, the warning list, and the Square history files. A sale record carries the customer's name, email and phone when one was attached. All of this is currently stored **unencrypted** in CloudKit, protected by the Apple ID and the share, not by a field key.

Never in iCloud: the Shopify token and app credentials, staff PINs and hashes, cashier passes, the AI assistant key, the open cart, the device's own settings (theme, tile size, register name, device mode and its switches), and the training or Demo data.

If encryption is switched on later, the likely split is: customer name, email and phone into `encryptedValues`, with the queryable numbers (totals, dates, register, staff) left plain so reports and the shop-wide sales view still work server-side.

## 8. Risks

- Owner Apple ID is a single point of failure (mitigated by keeping Shopify backups and adding a CloudKit export).
- Two CloudKit environments (Development and Production) can cause confusing "missing data" reports.
- The soft cart lock is only advisory.
- A device that stays on an old build after migration will keep writing to Shopify and diverge.
- Sync state while iCloud is signed out needs a clear UI.
